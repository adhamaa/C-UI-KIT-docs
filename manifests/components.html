## Accessibility

Built on [ui-sdk Menu](https://ui-sdk.dev/docs/react/components/menu), which follows the WAI-ARIA menu button pattern. The trigger has `aria-haspopup="menu"`, and the items are `menuitem`s.

| Key | Does |
| --- | --- |
| Enter, Space, ArrowDown | On the trigger, opens the menu on the first item |
| ArrowUp, ArrowDown | Move between items, skipping disabled ones |
| Home, End | First or last item |
| Typing | Jumps to the next item starting with the typed text |
| Enter, Space | Runs the item and closes the menu |
| Escape | Closes the menu and returns focus to the trigger |

On a table row, name each trigger after its row ("Actions for PKG-004"), so screen-reader users can tell the menus apart.

## Usage guidelines

**Do**

- Keep the row's main action as a visible button, and put the rest in the menu.
- Put destructive actions last, after a separator, with `danger`.

**Don't**

- Don't hide the only way to do something in a menu.
- Don't put more than about seven items in one menu. Group them, or rethink.

### The toggle

`AppShell.SidebarToggle` switches between full and `collapsedState` (`"mini"`, or `"hidden"`). It sets `aria-expanded` and `aria-controls`, and its name says what it will do: "Collapse sidebar" or "Expand sidebar". Pass `icon` to show your own icon.

### Compact screens

Below `breakpoint` (`"md"`, 62em, by default) the sidebar's children render in a drawer from the left instead. `AppShell.MenuButton` opens it, and it shows only on these screens; `SidebarToggle` hides. ## Styling

The layout is CSS grid, switched by media queries, so the page doesn't jump while it loads. Set these on `.kit-shell` (or with `style`):

| Variable | Default | What it sets |
| --- | --- | --- |
| `--kit-shell-bg` | `--kit-surface` | The page background |
| `--kit-shell-sidebar-bg` | transparent | The sidebar and drawer background |
| `--kit-shell-sidebar-full` | `300px` | Width when full (or `sidebarWidth.full`) |
| `--kit-shell-sidebar-mini` | `64px` | Width when mini (or `sidebarWidth.mini`) |
| `--kit-shell-drawer-width` | `min(20rem, 85vw)` | The drawer's width |
| `--kit-shell-transition` | `200ms` | How fast the width changes; `0ms` with reduced motion |

Attributes to style against: `data-layout`, `data-sidebar-state` (on the root and the sidebar), `data-compact` on the root, and `data-in-drawer` on the sidebar inside the drawer. Classes: `kit-shell`, `kit-shell__header`, `__sidebar`, `__main`, `__footer`, `__drawer`, `__backdrop`, `__toggle`, `__menu-button`.

The kit adds no padding, borders or cards: put your app's look on the parts with `className`.

## Accessibility

The drawer is built on [ui-sdk Drawer](https://ui-sdk.dev/docs/react/components/drawer).

- The parts are landmarks: `banner`, `navigation` (named "Main"; change it with `aria-label`), `main` and `contentinfo`.
- Hidden, the sidebar stays in the page at zero width but out of reach of the keyboard and screen readers.
- The drawer is modal: focus moves in and stays there, the page behind is inert, and focus returns to the menu button when it closes. Its heading, "Menu" by default (`drawerTitle`), is read out when it opens.

| Key | Action |
| --- | --- |
| <kbd>Enter</kbd> / <kbd>Space</kbd> on the toggle | Switches the sidebar between full and collapsed |
| <kbd>Enter</kbd> / <kbd>Space</kbd> on the menu button | Opens the drawer |
| <kbd>Tab</kbd> | Moves through the drawer, staying inside it |
| <kbd>Esc</kbd> | Closes the drawer |

## Usage guidelines

- **Do** keep your menu, logo and header in your app and pass them in as children.
- **Do** close the drawer when a link is followed (`closeMobile()`).
- **Don't** pad or round the shell's parts in the kit's CSS; style them in your app.
- **Don't** save the sidebar state inside the kit; control it and save it yourself.

- Use `focusableWhenDisabled` when a disabled button should still be reachable, for example to show a tooltip explaining why it's disabled.

## Usage guidelines

**Do**

- Keep one `filled` button per view, for the main action.
- Start labels with a verb: "Add package", "Export report".
- Put Cancel (`default`) before the primary action in dialog footers.

**Don't**

- Don't use a button to go to another page. Use a link.
- Don't change the label to "Saving…" while pending. The spinner and the screen reader announcement already say it's working, and a changing label shifts the button's width.
- Don't use `danger` for actions that can be undone.

## Related

- **Tooltip**: names an `IconButton` for mouse users.
- **ActionMenu**: when a row has more actions than fit as buttons.

## Examples

### Basic usage

`data` is the rows and `columns` is a list of AG Grid column definitions. Give rows a stable id with `tableSettings.getRowId`.

### Toolbar

- `title` on the left.
- A search box (`hasFilters`, on by default) that filters every column on the client, or calls `onSearchChange` on the server.
- `buttons` on the right. Each is `{ label, onClick, icon, variant, disabled }`, or `{ type: 'custom', component }` for your own.
- `refresh`, a button that spins while `isFetching`, and `hasReport`, a print button.
- `createRowBtn`, a button under the grid for adding a row.

### Number formatting

Set `type` on a column to format it: `currency` (Malaysian ringgit by default), `percentage` or `number`. Set `numberFormatting` in `tableSettings` to change the locale or currency.

With `tableSettings.autoFormatColumns`, columns named like amounts, percentages or counts are formatted without a `type`, as SWIFTO did.

<Canvas of={Stories.AutoFormattedColumns} />

### Row actions

`rowActions` returns, for each row, the items and how to show them: `type: 'tripleDot'` for a ⋮ menu, or `type: 'icon'` for one icon button per action. They sit in a column pinned to the right.

<Canvas of={Stories.IconActions} />

```tsx

  options: { type: 'tripleDot' },
  items: [
    { label: 'Open', onClick: () => navigate(`/packages/${rowData.uuid}`) },
    { label: 'Delete', danger: true, onClick: () => confirmDelete(rowData) },
  ],
})}
```

### Server-side paging and search

With `serverSide: true`, the table shows `data` as the current page and asks you for others:

- `totalRows`: the total on the server.
- `currentPage` and `onPageChange`: pages start at **0** here (unlike `Pagination`, which starts at 1).

<Canvas of={Stories.ServerSide} />

<Canvas of={Stories.SelectionAndTotals} />

By default the grid is capped at 62% of the viewport height (`tableContainerMaxHeight`). Set `height` for a fixed height, or turn off `pagination` to show every row.

### Basic usage

`Dialog` is controlled: you keep `opened` in state and close it in `onClose`. `onClose` runs on Escape, a press on the backdrop, or the × button.


### Composition

A Dialog is built from these parts, top to bottom. Every part except the body is optional.

| Part | Prop | Notes |
| --- | --- | --- |
| Header | `title`, `withCloseButton` | The title names the dialog for screen readers. The × button shows by default. |
| Description | `description` | Read out when the dialog opens. Text renders in a `<p>`, anything richer in a `<div>`. |
| Body | `children` | Scrolls when the content is taller than the screen. |
| Footer | `footer` | Actions, right-aligned. Put Cancel first and the primary action last. |

### Sizes

`size` takes a preset (`xs` 352px, `sm` 416px, `md` 512px, `lg` 720px, `xl` 960px, `full`), a number of pixels, or any CSS length. `fullScreen` fills the viewport.

### Required decisions

Turn off `withCloseButton`, `closeOnEscape` and `closeOnClickOutside` when the user must pick an action in the footer. Keep this rare: a dialog people can't dismiss feels like a trap.

`ConfirmDialog` asks a question and renders the Cancel and Confirm buttons for you. Return a Promise from `onConfirm` and the dialog stays open, with the confirm button pending, until it settles. It closes when the Promise resolves and stays open if it rejects, so you can show the error. Add `danger` for destructive actions.

## Accessibility

Built on [ui-sdk Dialog](https://ui-sdk.dev/docs/react/components/dialog), which follows the WAI-ARIA modal dialog pattern. The dialog sets `aria-modal`, is labelled by its title, and is described by its description.

| Key | Does |
| --- | --- |
| Tab, Shift+Tab | Moves through the dialog's controls, staying inside |
| Escape | Closes the topmost dialog and returns focus to the element that opened it (unless `closeOnEscape` is off) |

- Always give a dialog a `title`. Without one, screen readers announce an unnamed dialog.
- Opening by touch focuses the dialog itself, so no on-screen keyboard appears.

## Usage guidelines

**Do**

- Keep dialogs for short, focused tasks. Use a page for anything long or multi-step.
- Make the title a clear question or task: "Delete route?", "Edit package".
- Name the confirm button after the action ("Delete", "Publish"), not "OK" or "Yes".

**Don't**

- Don't open a dialog from another dialog. Change the content of the open one instead.
- Don't use a dialog for messages that need no decision. Use a `toast`.
- Don't use `ConfirmDialog` for actions that can be undone. Do the action and offer Undo in a toast.

## Accessibility

Built on [ui-sdk Select](https://ui-sdk.dev/docs/react/components/select), which follows the WAI-ARIA select-only combobox pattern. The trigger has the `combobox` role and the list is a `listbox`. The `label` names the trigger, and the description and error describe it.

| Key | Does |
| --- | --- |
| Enter, Space, ArrowDown | On the trigger, opens the list |
| ArrowUp, ArrowDown | Moves through the options, skipping disabled ones |
| Home, End | Goes to the first or last option |
| Typing | Jumps to the next option that starts with the typed text |
| Enter | Chooses the option, closes the list and returns focus to the trigger |
| Escape | Closes without choosing and returns focus to the trigger |

If a Select has no visible `label`, give it an `aria-label`.

## Usage guidelines

**Do**

- Always give it a `label`. The placeholder disappears once there's a value.
- Add `searchable` when there are more than about 10 options.
- Use option objects with stable IDs as values, so renaming a label doesn't break saved data.

**Don't**

- Don't use Select for two or three options. Show them all with `SegmentedControl` or `RadioGroup`.
- Don't load thousands of options at once. Use the server-side props or `InfiniteSelect`.
- Don't use the placeholder as a label or for instructions. Use `description`.

A time-of-day field, typed segment by segment: hours, minutes and, on a 12-hour clock, AM or PM. The value is always 24-hour `HH:mm`.

## Examples

### Clocks

`hourCycle` shows a 12 or 24-hour clock, and defaults to the locale's. `withSeconds` adds a seconds segment.

<Canvas of={Stories.Clocks} />

### Controlled

`onChange` receives `HH:mm` (or `HH:mm:ss` with seconds), or `null` while the time is incomplete or empty. That's true even when a 12-hour clock is shown.

<Canvas of={Stories.Controlled} />

### Min and max

`min` and `max` take `HH:mm`. A time outside the range is marked invalid.

<Canvas of={Stories.WorkingHours} />

## Styling

The box uses the **TextInput** classes. The segments are inside `.kit-time__input`, and each has `[data-type]` (`hour`, `minute`, `second`, `dayPeriod`) from ui-sdk.

## Accessibility

Built on [ui-sdk Time Input](https://ui-sdk.dev/docs/react/components/time-input). The field is a group named by its label, and each segment is a spinbutton named by its unit.

| Key | Does |
| --- | --- |
| Digits | Fill the segment and move to the next |
| ArrowUp, ArrowDown | Step the segment, wrapping around |
| Page Up, Page Down | Bigger steps |
| ArrowLeft, ArrowRight | Move between segments |
| Backspace | Empties the segment, then moves back |

## Usage guidelines

**Do**

- Store and send the 24-hour value. Let the field show the user's clock.

**Don't**

- Don't use it for durations ("2 hours 30 minutes"). Use `NumberInput`.

## Examples

### Events

Each event needs an `id` and a `title`. Add any of:

- `actor`: who did it, beside the title.
- `dateTime` (machine-readable, for the `<time>` element) and `time` (what's shown).
- `description`, and `metadata` as label/value pairs.
- `status` to colour the marker: `success`, `error`, `pending`, `info`, `warning` or `neutral`.
- `icon` inside the marker.
- For workflows: `department` and `stage` (shown after the actor as "Aina, Planning & Verification"), `reason` (like a rejection reason) and `sentFrom` (`{ name, department?, stage? }`, shown as a "Sent from" block).
- `date`, shown with `time`.

```tsx
<Timeline
  aria-label="Package history"
  events={history.map((h) => ({
    id: h.id,
    title: h.action,
    actor: h.user.name,
    dateTime: h.createdAt,
    time: formatDateTime(h.createdAt),
    status: h.action === 'Rejected' ? 'error' : 'success',
  }))}
/>
```

### Stages

`variant="status"` is roomier, for a workflow's stages rather than a dense log.

### Cards, alternating left and right

`appearance="card"` puts each event in a bordered card coloured by its status. With `variant="status"` the markers grow and show a status icon (a tick, a cross, a clock…), and the time shows as a pill. `alternating` adds SWIFTO's zigzag: a centred line, with events alternating left and right and the time on the opposite side.

<Canvas of={Stories.AlternatingCards} />

```tsx
<Timeline
  variant="status"
  appearance="card"
  alternating
  aria-label="Work order history"
  events={history.map((h) => ({
    id: h.uuid,
    title: h.action,
    actor: h.user.name,
    department: h.user.department,
    stage: h.stage,
    reason: h.remarks,
    sentFrom: h.from ? { name: h.from.name, stage: h.from.stage } : undefined,
    dateTime: h.created_at,
    time: formatDateTime(h.created_at),
```

# Toast

Short messages that appear in a corner and go away on their own: "Package saved", "Upload failed". Call `toast()` from anywhere, including outside components, like in a mutation's `onSuccess`.

<Source language="tsx" dark code={`import { toast } from '@adhamaa/ui-kit'`} />

<Canvas of={Stories.Kinds} />

`UIKitProvider` renders the `Toaster`, the place toasts appear, so `toast()` works with no setup.

## Examples

### Kinds

`toast(title)` shows a plain message. `toast.success`, `toast.error`, `toast.warning` and `toast.info` add an icon and a colour. Each takes a second `options` argument with a `description`.

```tsx
toast.success('Package saved')
toast.error('Upload failed', { description: 'The file is over 10 MB.' })
```

### Loading, then the result

`toast.loading()` shows a spinner and stays until updated. It returns an id: call another `toast` with the same `id` to replace it with the result.

<Canvas of={Stories.LoadingToResult} />

```tsx
const id = toast.loading('Exporting report…')
try {
  await api.exportReport()
  toast.success('Report ready', { id })
} catch {
  toast.error('Export failed', { id })
}
```

### Action

`action` adds a button, like Undo.

<Canvas of={Stories.WithAction} />

### Duration and dismissing

Toasts close after 4 seconds. Set `duration` in ms, or `Infinity` to keep one until it's dismissed. `toast.dismiss(id)` closes one, and `toast.dismiss()` closes them all. `onDismiss` runs when it closes.

<Canvas of={Stories.Persistent} />

## API

### toast(title, options?)

| Option | Type | Description |
| --- | --- | --- |
| `description` | `ReactNode` | A second line under the title |
| `duration` | `number` | In ms. `Infinity` keeps it until dismissed. Default 4000 |
| `id` | `string` | Reuse an id to update a toast instead of adding another |
| `action` | `{ label, onClick }` | A button in the toast |
| `onDismiss` | `() => void` | Runs when it closes |

Also `toast.success`, `toast.error`, `toast.warning`, `toast.info`, `toast.loading` (same arguments, each returns the id) and `toast.dismiss(id?)`.

### Toaster

Render it yourself only if you set `withToaster={false}` on `UIKitProvider`, for example to change where toasts appear.

## Accessibility

Built on [ui-sdk Toast](https://ui-sdk.dev/docs/react/components/toast). Toasts are announced by screen readers through a live region without moving focus. The timer pauses while the pointer is over a toast or focus is inside it, so people have time to read it and reach the action.

## Usage guidelines

**Do**

- Confirm actions people just took: saved, deleted, sent.
- Keep the title short, and put details in `description`.
- Offer Undo instead of a confirmation dialog for actions that can be undone.

**Don't**

- Don't use a toast for errors people must fix in a form. Show them next to the field.
- Don't put the only copy of important information in a toast. It disappears.

# Tokens

Every component reads its colours, radius, shadows, fonts and heights from CSS variables. The swatches below show the live values. Use the **Theme** and **Scheme** switches in the toolbar to see them change.

To change a token for your app, use `defineTheme()` or `extendTheme()`. See **Theming**. To use one in your own code, read the variable, or call `tokenVar()` in JavaScript:

```tsx
import { tokenVar } from '@adhamaa/ui-kit'

<div style={{ color: tokenVar('mutedForeground') }} />   // var(--ui-muted-foreground)
```

```css
.my-panel {
  background: var(--kit-surface-raised);
  border: 1px solid var(--ui-border);
  border-radius: var(--ui-radius);
}
```

## Colours

Variables named `--ui-*` are shared with ui-sdk. Variables named `--kit-*` are the kit's own. Each colour has a light and a dark value.

Pair each background token with its `…Foreground` token for text on it, so the contrast holds in both schemes.

## Accessibility

Built on [ui-sdk Tooltip](https://ui-sdk.dev/docs/react/components/tooltip). By default (`type="description"`) the label is added to the trigger's description, so screen readers read it after the trigger's name. With `type="label"` it becomes the trigger's name instead, for an icon button that has no `aria-label`.

- It opens on keyboard focus as well as hover, after `delay` (300ms).
- Escape closes it.
- Never put interactive content in a tooltip. It can't be reached with the keyboard.

## Usage guidelines

**Do**

- Keep it to a few words: name the action, or add one fact.
- Give every icon-only button a tooltip.

**Don't**

- Don't hide important information in a tooltip. People on touch screens rarely find it.
- Don't add a tooltip that repeats a visible label.

## Related

- **IconButton**: the usual trigger.
- **Popover**: for longer or interactive content.

## 1. Let npm find the package

The kit is a private package on GitHub Packages. Add this line to your app's `.npmrc`, next to `package.json`. It holds no secret, so commit it:

```ini
@adhamaa:registry=https://npm.pkg.github.com
```

Then give your own machine a token, once:

1. On GitHub, open **Settings → Developer settings → Personal access tokens → Tokens (classic)**.
2. Create a token with only the **`read:packages`** scope. GitHub's npm registry doesn't accept fine-grained tokens.
3. Add it to the `.npmrc` in your **home folder** (`~/.npmrc`, or `C:\Users\<you>\.npmrc` on Windows), never the project's:

```ini
//npm.pkg.github.com/:_authToken=ghp_your_token_here
```

**Deploy servers** (QA, prod, and the Docker build host) need the same line in their `~/.npmrc`. Use a token from a bot or machine account so deploys don't depend on one person. See *Server setup* in the repository README.

## 2. Install

```bash
yarn add @adhamaa/ui-kit
```

That's all most apps need. ui-sdk comes with the kit, so don't install `@ui-sdk/*` yourself: a second copy would split its React context. Requires React 19 or newer.

### Optional: tables and react-hook-form

Two parts of the kit live in their own entry points and need a library the kit doesn't install for you. Add one only if your app imports that entry point:

| If you import | Install |
| --- | --- |
| `@adhamaa/ui-kit/table` (`DataTable`) | `yarn add ag-grid-community ag-grid-react` (35 or 36) |
| `@adhamaa/ui-kit/form` (`RHF*` fields, `FormFields`, `FormDialog`) | `yarn add react-hook-form` (7.50 or newer) |

If you import one of these without its library, the build fails with a "module not found" error naming the package to add.

## 3. Load the styles once

**With Tailwind CSS v4**, at the top of your global stylesheet:

```css
@import "tailwindcss";
@import "@adhamaa/ui-kit/styles.css" layer(components);
```

The kit's stylesheet already includes ui-sdk's base styles. Putting it in Tailwind's `components` layer keeps Tailwind's base reset from undoing them, while utility classes still win. So `className="mt-4"` on any kit component works.

**Without Tailwind**, import it once at your app's entry, such as `app/layout.tsx` or `main.tsx`:

```ts
import '@adhamaa/ui-kit/styles.css'
```

## 4. Add the provider

```tsx
import { UIKitProvider, swiftoTheme } from '@adhamaa/ui-kit'

    </UIKitProvider>

}
```

| Import from | Contains | Needs |
| --- | --- | --- |

| `…/ui-kit/form` | `RHF*` fields, `FormFields`, `FormDialog` | react-hook-form |
| `…/ui-kit/table` | `DataTable`, AG Grid theme, cell editors | AG Grid |

# Theming

Every component reads its colours, radius and fonts from CSS variables. The colours that ui-sdk already defines keep its names (`--ui-primary`, `--ui-border`, …). The kit adds a few of its own (`--kit-success`, `--kit-table-header`, …).

## Use a preset

```tsx
import { UIKitProvider, neutralTheme, swiftoTheme } from '@adhamaa/ui-kit'

<UIKitProvider theme={swiftoTheme}>…</UIKitProvider>
```

- `neutralTheme`: slate greys with a blue primary. It's the default.
- `swiftoTheme`: SWIFTO's gold and slate palette, Helvetica / Noto Sans.

## Define your app's theme

```ts
import { defineTheme, extendTheme, neutralTheme } from '@adhamaa/ui-kit'

// From scratch: anything left out keeps the default.
export const claimsTheme = defineTheme({
  name: 'claims',
  colors: {
    primary: ['oklch(0.55 0.2 260)', 'oklch(0.7 0.15 260)'], // [light, dark]
    primaryForeground: 'white',                               // same in both
    primarySoft: ['oklch(0.96 0.03 260)', 'oklch(0.3 0.06 260)'],
  },
  scalars: { radius: '0.5rem', fontSans: '"Inter", sans-serif' },
})

// Or start from a preset.
export const myTheme = extendTheme(neutralTheme, { colors: { primary: '#0f766e' } })
```

A colour is a single CSS colour, or a `[light, dark]` pair. Pairs compile to CSS `light-dark()`, so changing scheme needs no re-render.

### Colour tokens

| Token | Variable | Used for |
| --- | --- | --- |
| `background` / `foreground` | `--ui-background` / `--ui-foreground` | Page and text |
| `muted` / `mutedForeground` | `--ui-muted` / `--ui-muted-foreground` | Quiet surfaces, secondary text |
| `border` / `input` | `--ui-border` / `--ui-input` | Dividers / field borders |
| `ring` / `ringBorder` | `--ui-ring` / `--ui-ring-border` | Focus glow / focused border |
| `primary` / `primaryForeground` | `--ui-primary` / `--ui-primary-foreground` | Filled buttons, checked controls |
| `primarySoft` / `primarySoftForeground` | `--kit-primary-soft` / `…-foreground` | Light buttons, selected options, current page |
| `destructive` / `destructiveForeground` | `--ui-destructive` / `--kit-destructive-foreground` | Errors, danger buttons |
| `success`, `warning`, `info` (+ `…Foreground`) | `--kit-success`, … | Badges, toasts, timeline |
| `surface` / `surfaceRaised` | `--kit-surface` / `--kit-surface-raised` | Dropzones / dialogs, cards, popovers |
| `tableHeader` / `tableHeaderForeground` / `tableRowHover` | `--kit-table-*` | DataTable |

### Scalar tokens

`radius`, `radiusSm`, `radiusLg`, `fontSans`, `fontMono`, `fontSize`, `lineHeight`, `spacing`, `shadow`, `shadowLg`.

## Theme with CSS only

You don't need the provider's theme. Pass `theme={null}` and set the variables in your own CSS:

```css
:root {
  --ui-primary: light-dark(#0f766e, #2dd4bf);
  --ui-primary-foreground: white;
  --ui-radius: 0.5rem;
}
```

To read a token in JavaScript, like for a chart, use `tokenVar('primary')`, which returns `'var(--ui-primary)'`.

Disabled and read-only fields have their own optional variables, so an app can give them a plain look without changing `--ui-muted` everywhere:

```css
:root {
  --kit-disabled-bg: #f8fafc;       /* default: var(--ui-muted) */
  --kit-disabled-border: transparent; /* default: var(--ui-input) */
  --kit-disabled-fg: #64748b;       /* default: var(--ui-muted-foreground) */
}
```

## Light and dark

```tsx
<UIKitProvider defaultColorScheme="auto">  {/* follows the OS */}
```

```tsx
import { useColorScheme, ColorSchemeToggle } from '@adhamaa/ui-kit'

const { colorScheme, setColorScheme, toggleColorScheme } = useColorScheme()
<ColorSchemeToggle />
```

The scheme sets `color-scheme` on `<html>`, plus `data-theme="dark"` and the `dark` class, so Tailwind's `dark:` variant works too. The user's choice is remembered in localStorage; turn that off with `persistColorScheme={false}`.

## The data table follows the theme

`DataTable` uses `createAgGridTheme()`, which is AG Grid's Quartz theme wired to the same variables. To use AG Grid directly elsewhere with the same look:

```tsx
import { createAgGridTheme } from '@adhamaa/ui-kit/table'

const gridTheme = createAgGridTheme({ rowVerticalPaddingScale: 0.8 })
<AgGridReact theme={gridTheme} … />
```

## Override one component

Every component accepts `className`, and form fields accept `classNames` per part (`root`, `label`, `control`, `description`, `error`):

```tsx
<TextInput label="Code" classNames={{ label: 'uppercase tracking-wide', control: 'bg-amber-50' }} />
```

The kit's styles live in the `ui-kit` cascade layer, so your classes win without `!important`.

# Forms with react-hook-form

Import from `@adhamaa/ui-kit/form`. Every kit field has an `RHF` version that takes the field's own props plus:

| Prop | |
| --- | --- |
| `name` | The form field. Required. |
| `rules` | Validation rules, as in `register`. `required` also shows the asterisk. |
| `defaultValue` | The field's default, if the form has none. |
| `control` | Only when the field isn't inside `<FormProvider>`. |

```tsx
import { useForm, FormProvider } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { RHFTextInput, RHFSelect, RHFDatePicker } from '@adhamaa/ui-kit/form'

const methods = useForm({ resolver: zodResolver(schema) })

<FormProvider {...methods}>
  <form onSubmit={methods.handleSubmit(save)}>
    <RHFTextInput name="package_name" label="Package name" />
    <RHFSelect name="state" label="State" data={states} />
    <RHFDatePicker name="start_date" label="Start date" />
  </form>
</FormProvider>
```

The kit doesn't depend on zod or any other schema library; use whichever resolver your app has.

## Infinite and server-searched selects

`InfiniteSelect` and `RHFInfiniteSelect` take one function that fetches a page. They debounce search, load more on scroll, cancel stale requests and remember labels of selected values:

```tsx
<RHFInfiniteSelect
  name="contractor_uuid"
  label="Contractor"
  initialOptions={record ? [{ value: record.contractor_uuid, label: record.contractor_name }] : []}
  loadOptions={async ({ search, page, signal }) => {
    const res = await services.contractors.list({ search, page: page + 1, per_page: 20 }, { signal })
    return {
      options: res.data.map((c) => ({ value: c.uuid, label: c.name })),
      hasMore: res.meta.current_page < res.meta.last_page,
    }
  }}
/>
```

It doesn't depend on TanStack Query. If your data already comes from `useInfiniteQuery`, pass it to a plain `Select` or `MultiSelect` with `data`, `hasMore`, `onLoadMore`, `loading` and `onSearchChange`.

## Config-driven forms

`FormFields` renders fields from an array, and `FormDialog` wraps that in a dialog with Cancel and Submit:

```tsx
import { FormDialog, openFormDialog } from '@adhamaa/ui-kit/form'

openFormDialog({
  title: 'Add item',
  fields: [
    { name: 'item_name', label: 'Item name', type: 'text', required: true },
    { group: [
      { name: 'unit', label: 'Unit', type: 'select', options: ['m', 'm²'] },
      { name: 'rate', label: 'Rate', type: 'number' },
    ] },
    { name: 'photo', label: 'Photo', type: 'custom', render: () => <MyUploader /> },
  ],
  onSubmit: (values) => createItem.mutateAsync(values), // stays open, pending, until it resolves
})
```

Field `type`s: `text`, `email`, `number`, `password`, `textarea`, `select`, `multiselect`, `radio`, `checkbox`, `switch`, `date`, `time`, `file`, `custom`. Pass any other prop of the underlying component through `props`.

## Binding your own component

```tsx
import { createRHFField } from '@adhamaa/ui-kit/form'

const RHFRating = createRHFField(Rating, ({ field }) => ({
  value: field.value ?? 0,
  onChange: field.onChange,
}))
```

The component receives `name`, `ref`, `error` (the message) and `withAsterisk` automatically.

# UIKitProvider

Applies a theme and hosts the toast region and modal stack. Place it once, near the root of the app. Every page of these docs is rendered inside one.

<Source language="tsx" dark code={`import { UIKitProvider } from '@adhamaa/ui-kit'`} />

```tsx
import '@adhamaa/ui-kit/styles.css'
import { UIKitProvider, swiftoTheme } from '@adhamaa/ui-kit'

export function Root() {
  return (
    <UIKitProvider theme={swiftoTheme} defaultColorScheme="light">
      <App />
    </UIKitProvider>
  )
}
```

## What it does

- **Theme:** injects a `<style>` tag with the theme's CSS variables. Pass a preset (`neutralTheme`, default, or `swiftoTheme`) or your own from `defineTheme()` / `extendTheme()`. Pass `null` when the app sets the CSS variables itself.
- **Colour scheme:** starts in `defaultColorScheme` (`auto` follows the operating system), and remembers the user's choice in localStorage unless `persistColorScheme={false}`.
- **Toasts:** renders the `Toaster`, so `toast()` works anywhere. Turn it off with `withToaster={false}` if you place `<Toaster />` yourself.
- **Modals:** renders the stack for `modals.open()` and `modals.confirm()`. Turn it off with `withModals={false}`.

With a Content Security Policy, pass `nonce` so the injected style tag is allowed.

## Next.js

The provider uses state and effects, so render it from a client component:

```tsx
// app/providers.tsx
'use client'
import { UIKitProvider } from '@adhamaa/ui-kit'
export function Providers({ children }: { children: React.ReactNode }) {
  return <UIKitProvider>{children}</UIKitProvider>
}
```

How to add a component to the kit, and how to document it so its page matches the rest. **Button**, **Select** and **Dialog** are the reference pages: copy one when you start.

## Where things live

```

```

## 1. Write JSDoc on the component

The props table is generated from it, so this is where most of the reference docs come from.

```tsx
export type BadgeProps = {
  /** @default 'light' */
  variant?: 'light' | 'filled' | 'outline' | 'dot'
  /** Content before the label, usually an icon. */
  leftSection?: React.ReactNode
}

/**
 * A short label for a status or a count.
 *
 * @example
 * <Badge color="success">Approved</Badge>
 */
export function Badge(props: BadgeProps) { … }
```

- One line per prop that says what it does, not what type it is.
- Add `@default` for every prop with a default.
- Give the component a summary and an `@example`.

## 2. Write the stories

One `.stories.tsx` file per component.

```tsx
const meta = {
  title: 'Components/Data display/Badge',
  component: Badge,
  tags: ['!autodocs'],          // the .mdx file is the docs page
  parameters: { layout: 'padded' },
  args: { children: 'Approved' },
  argTypes: {
    variant: { control: 'inline-radio', options: ['light', 'filled', 'outline', 'dot'] },
  },
} satisfies Meta<typeof Badge>

export const Playground: Story = {}
export const Variants: Story = { render: (args) => … }
```

- Start with a `Playground` story with no args of its own, so the Controls drive it.
- Spread `args` into `render` stories (`<Badge {...args} variant="dot" />`), so toolbar changes reach them.
- Use `fn()` from `storybook/test` for callbacks, so calls show in the Actions panel.
- Use realistic INFRACIVIC data: packages, routes, contractors, states. Avoid "foo" and "Lorem ipsum".
- For components with real interaction (pickers, overlays, tables), add `play` tests: open it, pick something with the mouse, do the same with the keyboard, and check focus. See `Select.stories.tsx` and `Dialog.stories.tsx`.

## Writing style

- Write for an app developer who has never seen the component.
- Use short sentences and the second person: "Pass `value` to control it."
- Lead each example with what it's for, then show it.
- Link to ui-sdk for behaviour the kit doesn't change. Only spell out what the kit adds.
- Show code people can copy: real imports, real prop names.

## Before you open a PR

- [ ] Every prop has JSDoc, with `@default` where it has one.
- [ ] Stories cover each variant, size and state.
- [ ] The docs page follows the template and renders with no errors.
- [ ] The **Accessibility** panel shows no violations on any story.
- [ ] `play` tests pass in the **Interactions** panel (if any).
- [ ] Both themes and both schemes look right (toolbar switches).
- [ ] `yarn lint`, `yarn type-check` and `yarn build-storybook` pass.
- [ ] A changeset if the package changed (`yarn changeset`).

## Publishing the docs

The docs are published to GitHub Pages at https://adhamaa.github.io/C-UI-KIT-docs/, from the public repo `adhamaa/C-UI-KIT-docs`. Until the org's GitHub Actions work again, publish by hand after a release or a docs fix:

```sh
yarn deploy-docs
```

It builds Storybook, generates the AI-readable text (`llms.txt`, `llms-full.txt` and a Markdown page per component, from the Storybook manifests), and pushes `apps/docs/storybook-static` to the `gh-pages` branch of the docs repo. You need push access to that repo. Set `DOCS_REPO` to publish somewhere else, for example a fork.

The kit's MCP server (see **Use with AI**) reads that text, so your JSDoc, stories and docs pages are what AI assistants learn from. Keep them complete, and run `yarn build-storybook && yarn build-llms` to preview the output in `apps/docs/storybook-static/llms/`.
